# Design

## Context

See [the proposal](proposal.md) for motivation and [the capability deltas](specs/) for behavior. Core already parses restricted DSX, resolves variants and fixtures, then extracts named states. The host owns project admission, current-source validation, immutable browser execution, and tool registration. The kit and renderer own canvas rendering; the preview can retain a last valid render even when the current source cannot be measured. Today's tools partially duplicate project loads and use independently bundled error classes. A new authoring feature must not introduce a separate renderer or let a retained preview masquerade as current evidence.

## Goals / Non-Goals

**Goals:** Keep one projection model and one canvas for preview and checks. Make tool selection and first-attempt arguments obvious. Keep public results bounded and machine-readable, errors recoverable, and old source files valid without migration. Make repeated UI and styling changes possible from versioned sources.

**Non-Goals:** No JS execution, template parameters, general nesting, multi-slot composition, arbitrary CSS selectors, stylesheet asset loading, automatic OS theme, real business logic, historical interaction replay, bulk screenshot export, live app capture, or host installation/restart automation.

## Decisions

### 1. Source ownership and layout composition

Use `layouts/<name>.dsx` with one `<Layout>` root and one empty `<ContentSlot />`; a screen selects it with a literal `layout="workspace"`. Metadata wrappers are stripped; only resolved kit nodes render. Allow normal interactive kit elements and navigation in shared source. Layout definitions do not declare Screen, Variants, another layout, parameters, or named state; each screen and its variant branches can select a layout independently and own their state. One screen-local namespace suffices because a layout is instantiated at most once per projection. Keep authored IDs unchanged; recalculate structural addresses after splice and retain original file and range. Detect expanded collisions against both slot content and fixture nodes; don't rename IDs or try to infer references. A bad dependency should mark affected projections, not unrelated screens.

Have a small source discovery policy supply a bounded inventory of config, tokens, layouts, declared stylesheets, screens, fixtures, and journeys to the loader, edit fingerprints and historical reader. Reuse the confined project-file admission rules; report unsupported, missing, oversized and escaping sources rather than loading a broader directory. Canonicalization and bounded reads happen before parsing. Build the layout catalogue independently, select the screen variant, compose the layout, expand fixtures, extract state, then validate the resolved tree and cross-screen targets. Collect dependent diagnostics without replacing source locations with the consumer's file. Make the Git revision reader use the same projection inputs from each requested revision, not current worktree layout, tokens, or CSS; the diff remains semantic rather than pixel-based. A copy/paste recipe would not propagate edits; reusable JSX imports would add execution and resolution semantics unnecessarily.

### 2. One palette resolver and one restricted stylesheet pipeline

Retain the base `tokens.json`; optional config `themes` names project-local override files under `themes/`, and optional `defaultTheme` selects a declared palette. Expose the base as the reserved effective name `base`. Parse base and override definitions with the same token helpers; merge raw token definitions with matching types, then resolve aliases in the merged table. Optional `colorScheme` metadata on a theme declares light or dark canvas form-control defaults, never the host color scheme. Seed semantic kit fallback values to match the current base appearance. Replace fixed kit colors on affected controls with semantic variables for surfaces, controls, and status foreground/background; this recolors Toast without changing its behavior. Clearly flag unknown explicit names and invalid merged palettes. Supply the resolved theme through preview payload and deterministic render options. A `theme` change updates the canvas variables without resetting compatible state; preserve it when building navigation and comparison URLs. Temporary review overrides do not ride a public URL. Copying screens per palette or relying on system preference would make approval links and evidence ambiguous.

Allow an ordered config `stylesheets` list of local files under `styles/`. Parse a restricted AST server-side: one simple class selector per rule, bounded rules/bytes, an allowlist of presentation/layout properties and values, and no resources, at-rules, imports, authored custom property definitions, or `!important`. Allow safe references to resolved token variables, but not source substitution or a second palette mechanism. Never forward raw files or authored selectors to the browser. A universal literal `styleClass` prop associates one or more names with the rendered component root. Resolve validated declarations against explicit node classes, merge by stylesheet order, and apply only to that canvas root through the existing scoped style machinery, using distinct generated keys and a canvas boundary. Precedence is kit defaults/props, then class rules in declaration order, then existing node `css`; class input cannot change another node's interaction metadata or style the DSH UI. Keep existing node-CSS local resource policy unchanged. Use one bounded declaration path for live and deterministic rendering. A global stylesheet or unrestricted descendant selectors would be harder to reason about and would couple authored DSX to internal DOM.

### 3. Shared render selection and compact measurements

Keep separate typed structural and rendered queries. For `design_view`, retain existing static and one-case inputs. `node` and `depth` scope the returned tree and, when combined with a breakpoint, the measured subtree; `open` is a text projection option, and cannot be submitted as a browser seed. The new geometry-only shape uses `mode: "geometry"`, a distinct `nodes` list of 1–24 stable IDs, and 1–6 ordered `cases` with required `breakpoint` and optional `state`, `theme`, and temporary `reviewContext`. Screen and variant are common to the call. Reject combinations with legacy per-case selectors; no implicit matrix or restarts. Return requested IDs in requested order with visible boxes, hidden/not-rendered status, or an absent-ID result. Filter before the result cap, not after a full DOM dump. Keep canvas geometry and per-case media findings separate. Do not return the tree as well in geometry mode. Query retains static globs, never uses the browser, and should direct mistaken render queries to View. A separate generic measurement/check tool would duplicate target discovery and render setup.

Resolve all cases before requesting the browser. Capture one current validated project and one bounded immutable file-backed media input set for the union of cases, using the existing passive-raster boundary. Share the captured bytes; resolve per-case references/media diagnostics using the same input. Each case gets a fresh page/context with its own seed on the existing warm session browser. Retain request order and respect cancellation and an overall timeout; do not silently return partial measurements as a pass. Return effective selectors and a source identity; include resolved render inputs, palette and styles in screenshot artifact identity. Keep screenshot persistence and inline delivery only on explicit capture. Journey theme selection is typed in authored DSX and applies across route changes. Layout lint accepts one theme at a time and retains its existing default breakpoint coverage.

### 4. Review coordinates are data, not a replay engine

Extend the existing comment context with effective theme, a complete overlay list, known tab selections, and authored-ID disclosure booleans, including explicit closed states. Keep older comments readable. In the owning session, submit this data only as part of the reviewed comment message; the agent can transcribe the compact typed coordinates into a measurement case. Resolve those coordinates against the current screen and branch over named state/defaults. If provided, the overlay list replaces the previous set; tab/disclosure maps override supplied keys only. Reject incompatible IDs, component types, or branch/screen drift that makes the inputs unusable; label a render from newer sources as a current rendition, not historical proof. Do not capture typed field values, synchronize live state with measurement, create sources, or allow any new side effect in the comment route. Avoid a comment reader or separate replay route.

### 5. Addressable kit controls without a generic action language

Draw new controls with existing kit metadata and hooks, keeping content/feedback, forms, and anchored overlays separate. `CodeBlock` reads a literal `text` prop, not whitespace-normalized JSX prose; support bounded text and a wrap option. `Callout` uses a title and children with a semantic tone, not unconditional live announcements. Keep `ToggleButton` boolean and `SelectButton` single-choice, storing both through the existing value interface; validate explicit disabled values and option IDs. Use native or equivalent keyboard semantics appropriate to each control. Add a propagated per-control part identity: the Tab ID resolves to its trigger for Tap without duplicating the addressable ID on its active panel; the panel retains separate ARIA linkage. Keep the identity available to comments, measurements and journeys without relying on hardcoded selectors per tool.

Give `Drawer` a token-backed width with a canvas-relative clamp; wire advertised shared overlay styles where supported. Let `Disclosure` opt into an expanded label; let `Input` opt into responsive growth on its field wrapper. Keep existing defaults if omitted. Expose an opt-in visual track on `Switch`, keeping its underlying switch semantics. Extract a small anchored positioning/focus primitive in the kit and use it for explicit Popover anchors and the SplitButton menu. Respect the current canvas and breakpoint, pointer/keyboard dismissal, focus return and disabled behavior; anchorless Popover keeps its centered presentation. SplitButton has distinct primary and menu triggers plus typed option selections; alternative actions are validated existing declarative references rather than string evaluation. No new Toast timing or dismissal behavior. Avoid rewriting all controls or making a universal overlay/controller class.

### 6. Thin tool registration, real dispatcher tests, and removal

Keep `tools.ts` an adapter: typed inputs, canonical results, short renderers, and small focused operations that take the existing project and browser ports. Reuse schema/boundary primitives supported by the deployed DSH version; validate cross-field rules at execution too. Reject unknown arguments, show accepted coordinates, and normalize expected browser/selection failures into a discriminated result by stable error code, not cross-bundle `instanceof`. Keep valid failed journey assertions and lint findings distinct from infrastructure outcomes. Embed immutable release/build identity at build time, including build identity for development artifacts, and expose the actual host/tools build identities if they differ. Don't inspect another installation to infer the active build. Project status remains non-launching and lists available targets. Optimize repeated project reads only where tests and read counts support it: current-source validation must not consume retained browser state, and automatic validation still detects generic shell writes and nested calls.

Keep `design_catalog` metadata-driven. Add a mutually exclusive `query` search mode with a small deterministic accent/case-normalized PT/EN index over canonical names, tags and curated synonyms; bound results (top eight) and return concise references or no match. Preserve exact and ordered batch lookups. Add linked runnable recipes for shared sidebar layouts, action bars, drawers, fixture data and the new controls. Validate example source in context and exercise representative interactive recipes in Chromium. Teach intent search and tool selection by replacing redundant prompt instructions, not by appending a second catalogue. Measure actual output and behavior through the installed dispatcher, not only a fake execute call.

Remove the `design_handoff` registration, package-specific planner, serializer and publication helpers once consumers have been checked. Keep the confined cache path and deterministic screenshot helpers; preserve any general source/projection readers used elsewhere. Remove or replace integration scripts, docs and prompt text that instruct owners to generate an export; leave archived OpenSpec history and existing user-generated cache files untouched. No wrapper or replacement exporter.

## Risks / Trade-offs

- **Projection drift between previews, Git revisions, journeys and browser evidence** — assert the same tree, layout source locations and effective style inputs at each consumer boundary; do not substitute current worktree files for historic inputs.
- **Layout composition changes IDs or introduces invalid targets** — retain authored IDs and both origins in diagnostics; validate every allowed branch and keep last-valid preview separate from current-source checks.
- **CSS escapes its canvas or affects deterministic measurement differently** — use a bounded grammar, explicit opt-in and generated scoped rules; exercise multiple canvases, owner-only review chrome, no-network checks, and cascade ordering in real Chromium.
- **Large measurements replace token cost with browser cost** — cap case and node counts, preflight before rendering, reuse the warm session browser and keep one time budget. Capture remains explicit.
- **Legacy appearance or accessibility regresses** — verify base defaults, focus return, keyboard operation, themes, high-contrast state distinctions, and mobile overflow in real browser tests. Prefer compatibility defaults over forced restyling.
- **One historic conversation overfits instructions** — use fixed, capability-valid real-model scenarios and independent deterministic contract tests; make no speed or precision claim from the historical trace alone.

## Migration Plan

Existing projects keep base appearance, source layout and legacy single-case calls. No project is rewritten at startup; keep projects with exact legacy kit pins renderable under the established compatibility policy. Authors opt into new files and selectors deliberately. Announce removal of the export tool in the release notes and direct users to authorized existing paths and source revisions. Leave prior generated packages as ordinary files. Reverting the plugin keeps legacy projects and exports intact; projects using new optional syntax require the newer plugin or a source revision from before opting in.
